## Fix Complexity Triage

### Larger or Policy-Heavy

- Code 2: bounded subprocess capture in the harness needs API/design work.
- Code 3: streaming or tailing harness logs is moderate because output behavior may change.
- Code 4 / Code 7: legal module bounded-read cleanup is broad.
- Code 8: inspection bundle evidence size budgets are an optional operational policy decision.
- Security 2 / Security 3 / Security 4: these are trust-boundary or policy decisions more than local
  hardening patches.

## Code Review Findings

### High

2. `harness/process.py::run_harness_command` still allows unbounded in-memory capture whenever
   callers pass `capture_output=True` or stdout/stderr pipes. Harness fixture/setup commands use this
   pattern in several places, so a noisy child process can still exhaust memory even though process
   timeouts now exist.

### Medium

3. `harness/runtime.py::summarize_trace`, `harness/runtime.py::write_job_summaries`,
   `harness/cli.py`, and `harness/backends/act/backend.py` read trace, summary, status, or log files
   into memory. Some reads are now bounded, but these harness-local files are generated by commands
   under test and should eventually be streamed, tailed, or bounded at all display points.

4. `legal/release_legal.py` still performs whole-file reads for curated legal files, local
   LICENSE/NOTICE files, Containerfiles, package metadata, and generated legal output. Most inputs are
   expected small, but the module would benefit from shared bounded helpers and clearer per-file size
   constants rather than ad hoc direct reads.

5. `release/commands/_shared.py::_append_github_outputs` writes directly to the path from
   `GITHUB_OUTPUT` and creates parent directories. This matches GitHub Actions behavior, but local or
   test execution with a surprising environment can write outside the workspace. Consider limiting
   this behavior to CI or avoiding parent-directory creation.

### Low

6. `release/process.py::run_logged_command` reads captured stdout/stderr back into memory when files
   are below `MAX_CAPTURED_OUTPUT_BYTES`. That is bounded, but callers that only need to stream logs
   should be audited so they do not request captured output unnecessarily.

7. `legal/release_legal.py::_read_legal_file_bytes` checks file size and then performs
   `Path.read_bytes()`. For untrusted paths this has a size-check/read race; use an opened file handle
   or shared bounded read helper if these inputs become less trusted.

8. `release/verification/inspection_bundle.py` intentionally copies retained evidence files so the
   inspection bundle is a self-contained snapshot, which is safer and easier to reason about than hard
   links. Because there is no per-file or total bundle size budget, very large retained staged or
   rebuilt artifacts can still increase peak disk usage while the temporary work area exists. Consider
   adding an explicit retention size budget if this becomes an operational issue.

## Security Review Findings

### Medium

2. `release/commands/materialization.py::_materialize_rc_git_content` executes a caller-provided
   `run_command` through `sh -lc`. This may be intentional for materialization, but it is a direct
   shell execution boundary and should be documented/gated accordingly, especially if configuration or
   workflow inputs are not fully trusted.

3. `release/verification/rebuild.py::run_host_direct_profile` executes configured rebuild commands on
   the host. This is expected for reproducibility verification, but it should remain a clearly labeled
   trust boundary and should not be reachable from unreviewed remote manifest data without local
   operator consent.

4. `release/verification/common.py::GpgVerifier` accepts signatures from any key imported from the
   downloaded KEYS file and does not bind releases to an expected signer fingerprint or role. That may
   match ASF project policy, but if per-release signer identity matters, verification needs an allow-list
   or manifest policy.

5. `release/commands/_shared.py::_append_github_outputs` trusts `GITHUB_OUTPUT` as an arbitrary
   filesystem path. In non-CI execution, a malicious environment can make release commands append to
   unexpected files.
